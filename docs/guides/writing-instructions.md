# Writing good instructions

The model sees the page as an accessibility tree: roles and visible names, not your CSS or your intentions. Write
steps the way you would brief a careful tester who has never seen the app.

## One goal per step

```ts
// Too much: three goals, and the step fails as a whole if one of them goes wrong.
await ai.act('Log in, open the settings, turn on dark mode and check it saved');

// Better
await ai.act('Log in as the admin', { secrets: ['password'] });
await ai.act('Open Settings and turn on "Dark mode"');
await ai.assert('Dark mode is on');
```

Each step is cached separately, so short steps also replay and heal more precisely.

## Name what is on screen, in quotes

Use the label the user sees: `Click "Add user"`, `Choose "Admin" in the Role dropdown`. If two elements share a label,
say which: `Click "Save" in the Notifications section`. Nudge's remedies often suggest exactly this.

## Data goes in `data`, secrets in `secrets`

```ts
await ai.act('Fill in the new user form', { data: { firstName: 'Thandi', email: gen.email() } });
await ai.act('Log in as the admin', { data: { username: 'admin' }, secrets: ['password'] });
```

Values in `data` are recorded as placeholders, so plans don't freeze one run's data, and generated values stay valid
(the server-side validators in the demo app check them). A secret only ever reaches credential fields; it never
appears in prompts, plans, events or reports. **Never write a secret in the spec**: traces include the source file.

Missing values can be generated by the model (`generate_value`), or by you with `gen` (SA ID, Luhn, IBAN, email,
phone, dates). Prefer `gen` when the value must be valid.

## Assertions: specific and visible

`ai.assert` judges what is on the page and, when it can, compiles a deterministic check for replays.

- Good: `"Thandi Mokoena" is in the user list`, `The status says "Profile saved"`.
- Weak: `It worked`, `The page looks right`. There is nothing specific to check, so nothing compiles.
- **Absence** (`No error is shown`) can't be compiled into a check, so it calls the model on every run. Add a code
  assertion next to it when you can.
- Where a code check is cheap, add one next to the AI assertion to catch a false pass.

## Hidden things: say where they are, or add a hint

Menus that open on hover, items inside collapsed sections, and virtualised lists are the most common failures. Either
say how to reach the element (`Hover "Settings" in the header, then click "Users"`), or write it once as a site hint:

```markdown
<!-- hints/localhost-5173.md -->
## Everywhere
- Users and Roles are in the Settings flyout in the header; hover "Settings" to open it.
```

Hints are added to every step's prompt on that site (or that path, under `## /users/**`). Keep them short and general;
`npx aipw hints lint` flags duplicates and files over the size cap.

## Let code do what code does well

- Logins and data seeding that aren't under test: code (API calls, fixtures).
- Repetitive, precise interactions you already have locators for: plain Playwright.
- Your own helpers can be called from English steps: `ai.tools.register({ name: 'create_user', … })`.

## When a step goes wrong

Run it in nudge mode (`npx aipw nudge spec.ts:LINE`), correct the AI (hint, pick, manual, options), and keep one of
the verified remedies: a better instruction, a site hint, or Playwright code ([07](../07-nudge-mode.md)).
